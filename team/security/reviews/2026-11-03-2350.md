## Findings

1. **Medium-high: code any agent can publish on this origin can now use Dinis's browser key (WS-132).** `db37b72` puts a key Dinis holds in his browser on web-summit.sgit.ai (`assets/keyring.js`, on every page). It is well built: standard ECIES (P-256, HKDF-SHA256, AES-256-GCM, random IV), the key imported **non-extractable** into IndexedDB, delivered in the URL fragment and cleared from the address bar, and the issuing agent's own copy stated plainly. But non-extractable stops copying, not use. Any script on this origin can open what is sealed to Dinis and sign as his browser. Three ways to get a script here:
   - **`javascript:` links pass through the markdown renderer.** I built a probe page with `[read me](javascript:onerror=eval;throw'...')` and it became a live link that runs arbitrary code on one click. Any `content/`, dashboard or board text could carry one. None exists today (checked).
   - **`people/<id>/pages.mjs`** (`44bce7e`, dev@web-summit.indi): the build imports and runs each person's module, in CI's release job too, with a write token. Its pages carry raw HTML and a `head` of scripts. Indi's loads its own `factory.js`, 9 lines and clean. Anyone with push could already edit `build.mjs`, so this is no new power, but it turns code execution into an ordinary "my folder" change that reviewers read as personal space.
   - **A person's own `app.js`** (the command-centre hook): none yet.
   The fix is in WS-132 (safe links, no raw scripts from people's folders) and WS-117 (the keyring and Ask Claude's key on an origin of their own). Until then, seal nothing real to a person key.
2. **Medium, by design: a person key issued by an agent is not the person's key.** `person-key.mjs` makes the key pair in the conductor's session and keeps the private half there (`~/.sg-send/issued/`). The tool says so honestly. It follows that a signature from "Dinis's browser" is equally one from the conductor's session, and what is sealed to Dinis is readable by it too. **Rule:** a signature from an issued person key must never stand as the person's own approval (sign-offs stay at level 1 until people hold keys they made themselves, WS-117). The unlock link carries the private key in clear, so it should travel only as a QR shown in person, never in a chat or an email. Smaller points:
   - The envelope's `by` and `at` are unsigned and not bound to the ciphertext (no AAD), so anyone can seal an item to Dinis that says it is from the conductor. Sign the envelope with the sender's key, or show "from" as unverified.
   - The key's fingerprint is computed over `crv:x:y`, not the DER SPKI that sgit and pki.sgit.ai use, so the same key would have two fingerprints across tools.
   - The key stays in the browser after its session ends; `lock()` exists, but nothing expires it.
3. **WS-116 fixed, verified** (`0fdfc91`, procurement@web-summit.silvio). `signoff.mjs` matches a key to its agent exactly (label's first word, or an `agent` field), binds the agent to its person (or Dinis's agents with `--on-word-of dinis`), refuses to write a statement that breaks either rule, and gate check 17 fails the build on a bad signature. Today: Dinis, Angelo and Vicky approved; four awaiting; none bad.

But the commit that published `conductor-3` on 1 November (`94ef8b0`) and the signing commit carry the same session (`session_018yvwtMPVc6R9iMzkBcVpE2`): one session, renamed. The entry's prose still says "conductor.3@web-summit"; WS-118 (status, expiry, proof) would make this self-evident.
5. **Writes outside a folder, all accounted for.** procurement@web-summit.silvio's `content/` pages are allowed since Silvio's decision on WS-101; its `validate.js` and `signoff.mjs` changes are the WS-116 fix I asked for.
