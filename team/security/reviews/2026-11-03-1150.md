## Findings

1. **WS-106 fixed, verified** (`a813cdc`, sgit@web-summit.dinis). `seal.mjs` now asks GitHub's activity API which account pushed the commit that brought a key to dev. It seals only if that account is on the roster for the key's person, or if the fingerprint was confirmed out of band (`--fingerprint`). Refusals do not print the fingerprint, and `pki-agent.mjs` must match a pinned sha256. That is the fix I asked for, and it answers the open question in "The push is the authorisation" for this repository. The roster is now the thing to protect: whoever can edit `data/team.json` can add an account to a person (WS-90, branch protection, still open).
2. **WS-123 item 5: the picker is a view, and `me.json` shows nothing new.**
   - The picker is labelled "View the site as" and keeps its choice only in this browser (`ws.me`). The code says "a view, not a sign-in", and **no other script reads `ws.me`**: not the feedback pane, not the command centres. Everything `me.js` writes into the page goes through `esc()`.
   - `me.json` holds, per person: name, role, colour, level, open, due and late issues, decisions with their stand-up source, agents with their last commit subject, the subjects of commits addressed to them, a 10-day count, the time of their ack, and links. All of it is already in the repository or on the pages, and the gate now scans it as shipped (`44595dc`).
   - One wording suggestion, low: the button reads **"Who are you?"** until a person is chosen. "View as..." says what it is; a question about identity reads like a login.
   - One rule for later: the day anything uses `ws.me` to say who *submitted* something (feedback, a sign-off, a vote), it becomes a forgery, as in WS-119. It must stay display only.
3. **Medium: Ask Claude keeps each person's OpenRouter key in this origin's localStorage** (`cc.or.key`, `8370ede`). The page says so plainly and asks for a key with a credit limit, which is right. The reach is wider than one page, though: localStorage is shared by the whole origin, and every person's `people/<id>/app/app.js`, which any of their agents may commit, runs on it. If Dinis opens Silvio's command centre in the same browser, Silvio's app could read Dinis's key. This is the same reason WS-117 asks for a signing origin of its own. Added to WS-117: the chat and its key belong on that separate origin (or behind the vault-held bounded key the page itself names as "next"). Until then, keep the key's credit limit small. The system prompt also carries the person's board, which many agents write; with no tools in the chat, that is material, not a risk.
4. **Low: two board files are WS-106.** `board/WS-106-meet-the-estate-s-repository-standard-the-gaps.md` (conductor, `44c61a6`) reuses the number of the key-pusher issue. Links and `Issue:` trailers that say WS-106 are now ambiguous. For conductor@web-summit.dinis: renumber the newer one.
5. **Watched, fine.** The 61 new briefing PDFs: no contact detail, key or token in their text. The sgit agent moved vault folders outside the clone, and `.sg_vault/` is now gitignored. `tag_release.sh` only adds the source commit to each versions row.
