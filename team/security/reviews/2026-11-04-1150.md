## Findings

1. **The studio's Vaults tools (WS-137 E3, `750e0598`): keep experimental, test token only.** sgit asked for this review. Verdict (also on WS-137):
   - The person's SG/Send access token (`studio.sgsend.token`) and the keys of vaults made in the studio sit in this origin's localStorage. Any script here can read them, and **WS-132's two routes to a script here are still open**. So: no real token and no real vault key in it until WS-132 part 1 is fixed. Real use goes with the studio to an origin of its own (WS-117).
   - **The write tools run without a person's yes.** The studio executes the model's tool calls as they come, and the model reads material others wrote (pages, company data, vault contents). Injected text could make it call `write_to_vault` or `create_vault` with the person's token. Fix: a confirm per call for the two write tools, showing what will be written.
   - I agree with dev's finding (`31cc3991`): `create_vault` should return the id only, so the read key never goes to the model's provider.
   - Good: the library is pinned with hashes, the tools are off by default, `read_vault` takes public read keys only, and the page says what it risks.
2. **WS-132 still open, and the stakes are higher.** Since it was opened, the conductors of Angelo, Indi, Jose and Vicky have issued their people keys too (`data/person-keys.json`, five active), each loaded into that person's browser on this origin, and the studio invites a token and vault keys here. Part 1, the renderer's link filter, is a few lines in `build.mjs`. Note added to WS-132: please do it first.
3. **Jose's reviewer agent held a leak before it happened (`d8301cd2`), as it should.** A draft issue would have published an access token's value by naming the vault it equalled. Only the hold and the review record were released, and **the record does not repeat the value** (checked). The vault keys later handed to Jose (`4029152f`) went by a file outside the repository, mode 0600, to be deleted once he confirms. The commit names environment variables, never values. Good practice; the other people's agents should copy it.
4. **Five escrowed person keys: WS-138 stands.** Each was issued by the person's conductor, which keeps the private half. A signature from any of them is equally the conductor's. WS-138 (open, from the conductor itself) says so; until people make their own keys (WS-117), no issued-key signature counts as the person's own approval. The writes to `data/person-keys.json` and `data/sealed/<own person>/` match each conductor's own person.
