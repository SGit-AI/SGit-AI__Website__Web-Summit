# The storm's data (WS-214)

JSON first: the incident dashboard ([/incidents/the-storm/](../../../../incidents/the-storm/index.html)), Vicky's agents and the work desk read these files, not pages. Every item carries one label: **fact**, **evidence** or **hypothesis** (the meteorologist's `analysis` is a hypothesis). Times are UTC (Lisbon's own time in November).

The dashboard reads `signals.json`, `decisions/graph.json`, `watch/websummit.json` and `weather/{warnings,stations,forecast,airport,analysis}.json`. A field it uses, renamed, breaks a pane (it says which file it could not read); tell incident.dev@ in a commit (`For: incident.dev@web-summit.dinis`) and it follows.

## signals.json

`node team/incidents/tools/timeline.mjs team/incidents/2026-11-10-the-storm`

`{ about, source, made_at, items: [ { at, approx, kind, label, key, text, sources: [{ label, url|null }] } ] }`, oldest first.

- Reads only the table rows whose first cell looks like `10 Nov, 17:42` (or `~17:42`); the paragraphs under the table are not read.
- `kind`: `signal` when the text starts "signal" (`signal:`, `signal (unofficial):`, kept as "(unofficial) …") or the source is relayed "via social.watch@"; `official` when the source names IPMA, portugal.gov.pt, websummit.com, ANEPC, S41 or the weather desk; `team` otherwise (our own record).
- `label`: `evidence` for a signal, `fact` otherwise. `key`: the row was in bold. `approx`: the time had a `~`. Only https links are kept as URLs.

## watch/websummit.json

`node team/incidents/tools/websummit.mjs team/incidents/2026-11-10-the-storm`

`{ about, read_at, watch, sitemap: { source, count, added_this_read: [url], urls: { url: first_seen } }, blog: { source, listings: [url], posts: { url: { url, title, category, date, modified, excerpt, first_seen } } }, bluesky: { source, posts: [{ at, text, url, match }] }, alerts: [{ first_seen, channel, url, text, at?, label }], errors: [] }`

- **Why the blog (J6):** the Day 2 decision went up at 19:09 on `/blog/web-summit/important-event-update-2026/`, which no sitemap lists; we learned of it 43 minutes later, from the press. Every blog listing is now read, and a category named only by a post (e.g. `partners`) is read too. A blog alert is `new` (a post not seen before), `modified` (its `modified` changed) or, on the first read only, `recent` (published or modified in the last 36 hours). The WordPress REST API answers 404 on this site (a Next.js front end), so the listings' embedded data is the one read.
- An **alert** is a new blog post or a changed one (above), a new sitemap URL or an own post whose text matches `watch` (since 20:04 also Thursday/quinta, day 2 and 3, PITCH, tickets, refunds, talks, speakers, streams, side events: the open items after the Wednesday decision). It is a fact that the organiser published it; **a match is not a decision**: read it.
- The first read records the URL set and the newest post and raises no alert; after that only a new URL, or a post newer than the last read's newest, can raise one. `alerts` keeps every alert ever raised, with `first_seen`.
- The dashboard also reads Bluesky **live in the browser** every minute (its public API allows any origin), so a post shows on the page without waiting for this file, CI or Pages' cache. The sitemap has no such header, so it needs this connector.

The weather connectors are the meteorologist's own (`weather/tools/refresh.py`). The researcher's parser asks (`decisions/sources.json`, `parser_ask`) are next.
