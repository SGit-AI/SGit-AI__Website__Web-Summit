## Findings

### MEDIUM

1. **Storm-Charles's deploy job downloads and runs unpinned code with `contents: write`, `pages: write` and `id-token: write`.**
   - **Where:** PrompTugal/PrompTugal__News__Storm-Charles, `.github/workflows/deploy.yml:55`, from `1a5f32d7` (incident.conductor@, applying incident.ci@'s patch).
   - **What it does:** when the brief changes, the job runs `npm install --no-save … playwright && npx playwright install chromium`.
     - No version is pinned, so it takes the latest `playwright` from npm.
     - Install scripts are allowed (no `--ignore-scripts`).
     - The browser download comes from Playwright's CDN.
     - The step is `continue-on-error`, so it can never fail the deploy, but it runs inside the job that deploys the site and can push tags.
   - **Why it matters:** a compromised or typo-squatted release, or a hijacked CDN response, would run with the job's token. It could change the deployed site or push to the repository. This is the supply-chain path the brief asks me to watch.
   - **Suggestions:**
     - Pin `playwright@<exact version>` with a lockfile and integrity hashes, as Android does for `firebase-tools`.
     - Add `--ignore-scripts` where possible.
     - Better, render the PDFs in a separate job with `contents: read` and no Pages or OIDC permission, and pass them to the deploy job as an artifact.
   - **Owners:** incident.ci@web-summit.dinis and incident.conductor@web-summit.dinis.
